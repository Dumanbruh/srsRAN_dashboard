# Техническое задание
## Расширение srsRAN Control Dashboard: рабочий инструмент мониторинга и управления сценариями 5G SA Open RAN testbed

**Заказчик:** Думан Марламбеков (KazNU, DigitAlem LLP)
**Исполнитель:** реализация через Claude Code (консольный клиент) на сервере `srsran`
**Дата:** 13.08.2026

---

## 1. Цель и контекст

Существует Django-дэшборд управления 5G SA Open RAN testbed (сервер `srsran`, Ubuntu 24.04.4, Open5GS + srsRAN Project 25.10.0 + srsUE + GNU Radio/ZMQ + FlexRIC/E2SM-KPM, метрики в InfluxDB, данные в MongoDB, LLM-ассистент на Ollama qwen2.5:7b-instruct).

Требуется **расширить** существующий дэшборд, превратив его в единый рабочий инструмент для:
1. мониторинга живых и исторических метрик testbed;
2. запуска управляемых сценариев (базовые сценарии подключения, готовые эксперименты из исследовательских работ, произвольные конфигурации).

Дэшборд не публичный, однопользовательский, без системы авторизации.

## 3. Функциональные требования

### 3.1. Мониторинг метрик

- **Live-режим:** графики в реальном времени (обновление с настраиваемым интервалом, напр. 1–5 сек) по метрикам, снимаемым с E2SM-KPM/InfluxDB — RTT, throughput (UL/DL), packet loss, состояние handover, буферизация (bufferbloat-метрики), число подключённых UE, состояние slice (eMBB/URLLC/mMTC при наличии PPO-slicing сценария).
- **История:** просмотр данных за выбранный период (диапазон дат/времени), с возможностью зумирования графика.
- **Экспорт:** выгрузка выбранного диапазона в CSV; генерация краткого отчёта (PDF или HTML) с графиками и сводной статистикой по прогону/периоду.

### 3.2. Управление сценариями

Панель запуска/остановки сценариев с логами выполнения в реальном времени (streaming логов в UI) и статусом (idle / running / completed / failed).

**a) Базовые сценарии подключения**
- Запуск/остановка core (Open5GS), gNB (srsRAN), UE (srsUE) по отдельности или как единая цепочка "поднять сеть".
- Индикация состояния каждого компонента (запущен/остановлен/ошибка), с последними строками логов.

Сценарии описываются декларативно (YAML/JSON) как последовательность шагов (запустить компонент X с параметрами, подождать/проверить готовность, применить нагрузку, снять метрики, остановить компонент) — это отдельный "движок сценариев", исполняющий описание, а не жёстко закодированные функции. Это позволяет добавлять новые сценарии без изменения кода дэшборда.

**b) Готовые сценарии экспериментов** (на основе выполненных исследований)
- **Handover:** сценарий эмуляции перемещения UE между сотами/incят с записью метрик для gradient-boosted trees предсказания handover.
- **Bufferbloat / нагрузочный тест:** сценарий с несколькими UE и управляемой нагрузкой (аналогично экспериментам S1–S4 из статьи), сбор RTT под нагрузкой.
- **PPO SLA-slicing:** сценарий с несколькими активными срезами (eMBB/URLLC/mMTC) и профилем нагрузки для сравнения политик распределения PRB.
- **Early-warning:** длительный прогон с сохранением временных рядов транспортного уровня для последующего обучения/проверки модели раннего предупреждения о bottleneck.
- Каждый сценарий: параметризуемый (длительность, число UE, профиль нагрузки), с шаблонами "по умолчанию" под каждую статью.

**c) Произвольная конфигурация**
- Форма, где пользователь задаёт параметры вручную (число UE, полоса, mobility pattern, slice-профиль и т.д.) и запускает как разовый сценарий.

**d) История прогонов**
- Список выполненных сценариев (когда, какой тип, параметры, статус, ссылка на собранные данные/экспорт).

---

## 4. Нефункциональные требования

- Технологии: Python/Django (продолжение текущего стека), сохранить интеграцию с InfluxDB, MongoDB, Ollama.
- Устойчивость: запуск/остановка сценариев не должна require перезапуск дэшборда; при падении сценария — корректный статус failed + причина.
- Логи хранятся (для истории прогонов), метрики продолжают писаться в InfluxDB как сейчас.

---

## 5. Принятые решения

- **Запуск компонентов:** способ запуска Open5GS/gNB/UE на сервере сейчас не унифицирован (где-то bash, где-то вручную). Первым шагом реализации нужно ввести единый слой абстракции — process manager внутри Django (обёртка над subprocess, с возможностью в будущем переключиться на systemd/docker), который выступает "исполнителем" шагов сценария. Это обязательная часть аудита (см. п.6, шаг 1).
- **Движок сценариев:** гибкий, декларативный (YAML/JSON), см. п.3.2.
- **Экспорт:** только CSV с данными (без графика/отчёта на первой итерации).

## 7. Порядок реализации (для Claude Code на сервере)

1. **Аудит:** существующий Django-проект (структура приложений, модели, views/шаблоны, способ получения метрик из InfluxDB); отдельно — аудит того, как СЕЙЧАС фактически запускаются Open5GS/gNB/UE на сервере (какие команды, конфиги, где лежат).
2. **Process manager:** единый слой запуска/остановки/статуса произвольного компонента (subprocess-based), с потоковым выводом логов.
3. **Движок сценариев:** формат описания сценария (YAML/JSON), исполнитель шагов поверх process manager, модель данных (Scenario, ScenarioRun, RunLog).
4. Перевести в декларативный формат 4 готовых сценария: базовое подключение, handover, bufferbloat/нагрузка, PPO SLA-slicing, early-warning прогон.
5. **UI:** страница мониторинга (live + история + CSV-экспорт), страница сценариев (каталог + запуск + статус/логи в реальном времени + история прогонов).
6. Тестирование на реальном testbed на одном из сценариев (например, базовое подключение → handover) end-to-end.
